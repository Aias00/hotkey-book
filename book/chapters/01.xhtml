第一章 从一个热商品开始

假设一个商品详情服务有一百个实例，正常流量分散在百万个商品上。一次直播突然把大量访问集中到同一个商品，即使 Redis 的总容量足够，负责这个键的分片也可能率先过载。此时增加缓存容量并不直接解决单键压力；我们需要把频繁读取移到业务 JVM，减少到达后端的请求。

HotKey 做的第一件事不是缓存商品，而是发现哪些键值得特殊处理。它把业务调用转换成键计数，在 worker 汇总，达到规则阈值后把热点身份推送到客户端。业务随后决定缓存、限流还是返回降级内容。探测框架与业务动作之间的这个边界，是阅读全书的起点。

为什么需要集群汇总

一个用户每秒请求五百次，分散到一千个业务实例后，许多实例在一秒内一次也看不到。如果各实例只按自己的计数判定，这个用户可能一直不会触发阈值。客户端先合并本机计数，再把同一个键路由到同一个 worker，才能在集群维度观察它。

这里的“集群维度”依赖客户端对 worker 列表和规则具有相容的认识。网络分区、成员变更和发送失败都会影响统计；它不是跨机器事务计数器。适合用它发现突发热点，却不能直接把它当成订单配额或资金扣减依据。

本书怎样使用证据

本书依据当前仓库的源码编写，基线为提交 f1c8181，父工程版本为 0.0.4-SNAPSHOT。源码说明的是这个快照的行为；改进建议明确写为建议。原 README 的京东大促数据是项目历史自述，本书没有重跑相同压测，不把它们当成你的容量承诺。

读者应能读懂 Java 方法、线程和基本缓存概念。先读第二章建立模块地图，再沿第三至第七章追一次完整请求，最后用部署、实验和故障章节检验理解。每章末的问题可以作为团队源码走读的讨论题。

思考

一个总 QPS 很低、但每次读取都昂贵的接口是否需要热点探测？请同时考虑探测成本、触发时延和本地值的更新成本。判断依据应是节省的后端工作量，而不只是访问次数。
