第三章 设计规则与业务键

KeyRule 包含 key、prefix、interval、threshold、duration 和 desc。interval 是探测窗口秒数，threshold 是窗口内累计阈值，duration 是变热后的保留时长。窗口长度与热点寿命解决不同问题：前者判断是否热，后者控制特殊处理保持多久。

一个可解释的规则

{
  "key": "sku__",
  "prefix": true,
  "interval": 2,
  "threshold": 10,
  "duration": 60,
  "desc": "实验商品热点"
}

这只是规则对象的示意，不是可直接提交到任意 dashboard API 的完整请求。它表达两秒窗口累计十次后判热，并保留六十秒。部署时通过控制台为正确的 appName 创建规则，再检查客户端已收到规则。

业务键可以采用 sku__42、user__123、api__detail 等形式。前缀应同时表达对象类型和治理动作。若用同一个键混合“展示商品”和“更新商品”，统计将难以解释。包含租户、地区或版本时，应选择与值内容一致的维度；否则可能把一个租户的本地结果复用给另一个租户。

参数怎样影响行为

阈值太低会把大量普通键提升为热点，推送和本地缓存的成本上升；太高会错过短促尖峰。duration 太长会延长陈旧数据风险，太短则反复推送和填充。先测常态分布和尖峰持续时间，再选择参数，比直接复制别人的阈值可靠。

KeyRule.Builder.interval 会把小于一的输入改为一，duration 也有类似处理。但公共构造器直接赋值；不能由 Builder 的检查推断所有入口都完成了校验。对管理端输入的正数、上限和重叠规则顺序，应结合对应接收路径另行验证。

规则不是免费索引

探测单个用户很有用，但随机生成海量唯一键会增加客户端集合、worker 窗口和垃圾回收压力。应限制键长度，选择稳定维度，并估算一个窗口内活跃键数量。使用通配规则前，先明确它是否会把无需治理的流量一起纳入。

练习

为商品读取和恶意用户分别设计规则。写下触发后的动作、错误判热代价、漏判代价及最长可接受延迟。两种业务不应只因为流量相同就使用同一套规则。
